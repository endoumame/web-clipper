# web-clipper 新機能提案 - 2026-04-30

## エグゼクティブサマリー

前回提案（2026-04-01）の High 優先度 2 件（AI 自動タグ付け・ハイライト注釈）が実装完了しました。2026 年の Web クリッパー市場では AI インタープリター、コンテキスト認識型リコール、AI 入力パイプラインが主要トレンドです。本提案では、競合ギャップ分析に基づきブラウザ拡張機能と AI インタープリターを最優先として 8 件の新機能を提案します。

## 現状の機能セット

- 記事クリッピング: URL 指定で OGP・タイトル・説明文を自動抽出し、11 種以上のソースタイプに分類する
- コンテンツ抽出: Readability + Turndown による HTML→Markdown 変換・保存
- AI 要約: Cloudflare Workers AI（llama-3.1-8b-instruct）による記事要約生成
- AI 自動タグ付け: 既存タグ優先の自動タグ提案・適用（2026 年 4 月実装）
- ハイライト・注釈: テキスト選択→色分けハイライト、オフセットベース位置保存、注釈メモ（2026 年 4 月実装）
- 記事管理: CRUD 操作、既読/未読ステータス、メモ、ページネーション
- タグ管理: カスタムタグ作成・フィルタリング・検索ドロップダウン
- 検索・フィルタリング: タイトル/説明文の全文検索、ソースタイプ・タグ・既読状態フィルタ
- 認証: ユーザー名/パスワード + GitHub OAuth 2.0、Cookie セッション管理
- PWA 対応: Web Share Target API による OS 共有メニュー統合
- UI/UX: ダーク/ライトモード、View Transitions API、UNO CSS
- API ドキュメント: OpenAPI 3.0 仕様 + Scalar UI インタラクティブリファレンス
- インフラ: Cloudflare Workers + D1（SQLite）+ Workers AI

## 新機能提案

### 優先度: High（すぐに着手すべき）

#### 提案 1: Chrome ブラウザ拡張機能

- 概要: Manifest V3 ベースの Chrome 拡張機能を開発する。ワンクリックで閲覧中のページをクリッピングし、右クリックメニューから選択テキストをハイライト付きで保存する。サイドパネルモードでページを離れずにクリッピングを完結できる
- ユーザー価値: 現状では URL の手動コピーと Web アプリへの貼り付けが必要である。拡張機能によりブラウジング中のワンクリック保存が実現する。全主要競合がブラウザ拡張を提供しており、必須の機能である
- 実装難易度: Medium
- 技術的アプローチ:
  - Manifest V3 + Vue 3（popup/sidepanel UI）で新パッケージ `apps/extension` を作成する
  - 既存の Hono API エンドポイント（`POST /api/articles`）をそのまま利用する
  - Content Script でページ内 DOM を取得し、ペイウォール内コンテンツもクリッピング可能にする
  - `packages/shared` の Zod スキーマを拡張機能でも共有して型安全性を維持する
  - Cookie 認証または API トークン認証を選択する。拡張機能用にトークンベース認証の追加を検討する
  - 選択テキスト→ハイライト API（`POST /api/articles/:id/highlights`）と連携する
- 参考実装: Obsidian Web Clipper（30 万 DL 超、サイドパネル対応）、Notix（Notion 向け、AI 事前入力）

#### 提案 2: AI インタープリター（自然言語による構造化抽出）

- 概要: 記事保存時にユーザー定義の自然言語プロンプトでコンテンツから構造化データを抽出する。「この記事の主要な論点を 5 つ抽出して」「技術スタックを列挙して」などのテンプレートを定義できる
- ユーザー価値: 現在の AI 要約は一律フォーマットだが、求める情報はユーザーごとに異なる。インタープリターにより記事の種類に応じたカスタム抽出が可能になる。Obsidian Web Clipper で最も評価されている機能である
- 実装難易度: Medium
- 技術的アプローチ:
  - ドメイン層に `InterpretationTemplate` エンティティを新設する。テンプレート名、プロンプト、URL パターントリガーを持つ
  - `application/commands` に `InterpretArticleCommand` を追加する
  - Cloudflare Workers AI の既存バインディングを活用して抽出プロンプトを LLM へ送信する
  - 抽出結果は Article のメタデータとして JSON 形式で D1 に保存する
  - URL パターンでテンプレートを自動適用する（例: `qiita.com/*` → 技術記事テンプレート）
  - フロントエンドにテンプレート管理 UI（Vue 3 コンポーネント）を追加する
- 参考実装: Obsidian Web Clipper Interpreter（`{{"summary of the page"}}` プロンプト変数）、Readwise Ghostreader

### 優先度: Medium（次のマイルストーンで検討）

#### 提案 3: 全文コンテンツ検索（FTS5）

- 概要: 記事の Markdown コンテンツ全体を対象とした全文検索を追加する。タイトル/説明文検索を拡張し、本文内キーワード検索を可能にする
- ユーザー価値: 記事数が増えるほど目的の記事を見つけにくくなる。本文検索により断片的な記憶からでも目的の記事へ到達できる
- 実装難易度: Low
- 技術的アプローチ:
  - D1（SQLite）の FTS5 仮想テーブルを活用する。Drizzle マイグレーションで `articles_fts` テーブルを作成する
  - 既存の `ArticleQueryService` を拡張して FTS5 `MATCH` クエリをサポートする
  - `GET /api/articles` のクエリパラメータに `contentSearch` を追加する
  - フロントエンドの検索 UI に「本文も検索」トグルを追加する
- 参考実装: Readwise Reader（全フォーマット横断検索）、Karakeep（AI + 全文検索併用）

#### 提案 4: プラットフォーム別コンテンツ抽出器

- 概要: Reddit（JSON スレッド）、YouTube（トランスクリプト+メタデータ）、GitHub（README+メタデータ）など、プラットフォームごとに最適化した抽出ロジックを実装する
- ユーザー価値: 汎用 Readability では取得できないプラットフォーム固有のコンテンツを正確に保存できる。Reddit のスレッド構造、YouTube の字幕、GitHub の README が該当する。既存の `Source` 値オブジェクトで 11 種のソースを分類しており、それを活用した拡張が自然である
- 実装難易度: Medium
- 技術的アプローチ:
  - `infrastructure/services` に `PlatformExtractor` インターフェースと各プラットフォーム実装を追加する
  - 既存の `Source` 値オブジェクト（Twitter、Qiita、YouTube 等）をキーにストラテジーパターンで抽出器を選択する
  - YouTube は `youtubei` API または oEmbed + 字幕取得、Reddit は JSON API（`.json` サフィックス）を利用する
  - 既存の `MetadataFetcher` ドメインサービスを拡張してソースタイプ別の抽出器へディスパッチする
- 参考実装: Web2MD（9+ プラットフォーム対応）、Obsidian Web Clipper（Schema.org データ抽出）

#### 提案 5: Markdown エクスポート（フロントマター付き）

- 概要: 保存済み記事を YAML フロントマター付き Markdown ファイルとしてエクスポートする。Obsidian Vault 等の PKM ツールとの連携を実現する
- ユーザー価値: 多くのユーザーが Obsidian や Logseq 等の PKM ツールを併用している。フロントマター付きエクスポートにより、クリッピングした記事をそのまま PKM に取り込める
- 実装難易度: Low
- 技術的アプローチ:
  - `application/queries` に `ExportArticleQuery` を追加する
  - フロントマターに title、url、tags、source、createdAt、aiSummary を含める
  - `GET /api/articles/:id/export?format=markdown` エンドポイントを新設する
  - フロントエンドにエクスポートボタン（単体/一括）を追加する
  - 一括エクスポート時は ZIP を生成する。Cloudflare Workers の制約内で実装可能である
- 参考実装: Readwise Reader（Obsidian/Notion/Logseq エクスポート）、Obsidian Web Clipper（ネイティブ Markdown 保存）

### 優先度: Low（長期的に検討）

#### 提案 6: ハイライト間隔反復（Spaced Repetition）

- 保存したハイライトを最適な間隔で再表示し、記憶定着を促進する
- Cloudflare Cron Triggers で定期実行する。メールダイジェストまたはアプリ内通知として配信する
- Readwise Reader の看板機能（音声デイリーレビュー含む）を参考に軽量版から開始する
- 実装難易度: Medium

#### 提案 7: Webhook / 自動化 API

- 記事クリッピング・タグ付け等のイベントを Webhook で外部サービスへ通知する
- Zapier/Make/n8n 等と連携し、クリッピング→Notion/Slack 通知等の自動化を実現する
- D1 に `webhooks` テーブルを追加する。イベント発火時に Workers 内で HTTP リクエストを送信する
- 実装難易度: Low
- 参考実装: Readwise Reader Webhooks API

#### 提案 8: RSS/Atom フィード購読

- RSS フィードを登録して新規記事を自動的にクリッピングする
- Cloudflare Cron Triggers でフィードポーリング（15 分〜1 時間間隔）を実行する
- `Feed` 集約をドメイン層に追加して自動クリッピングのルール設定を可能にする
- 実装難易度: Medium
- 参考実装: Readwise Reader（15+ フォーマット統合受信箱）

## DDD / クリーンアーキテクチャ観点のメモ

### ドメイン層への影響

- 提案 1（ブラウザ拡張）はドメイン層への変更が最小限である。認証方式を追加する場合は `Session` 集約の拡張か `ApiToken` エンティティの新設を検討する。拡張機能は `apps/extension` として独立パッケージとする
- 提案 2（AI インタープリター）は `InterpretationTemplate` を新集約として `domain/interpretation/` へ配置する。`Article` 集約に interpretations フィールドを追加するか、独立集約として分離するかの設計判断が必要である
- 提案 3（全文検索）はドメイン層への影響がない。インフラ層のクエリサービスとプレゼンテーション層のみ変更する
- 提案 4（プラットフォーム別抽出器）は `ContentExtractor` ドメインサービスのストラテジーパターン化が必要である。既存の `Source` 値オブジェクトとの連携が自然である

### レイヤー配置方針

| 提案 | ドメイン層 | ユースケース層 | インフラ層 | プレゼンテーション層 |
|------|-----------|--------------|-----------|-------------------|
| ブラウザ拡張 | ApiToken（新規） | — | トークン永続化 | 拡張機能 UI（別パッケージ） |
| AI インタープリター | InterpretationTemplate | InterpretArticleCommand | Workers AI 呼び出し | テンプレート管理 UI |
| 全文検索 | — | — | FTS5 クエリ拡張 | 検索 UI トグル |
| プラットフォーム別抽出器 | — | — | PlatformExtractor 実装群 | — |
| Markdown エクスポート | — | ExportArticleQuery | Markdown 生成 | エクスポートボタン |
